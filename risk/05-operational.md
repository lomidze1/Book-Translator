# R-11, R-13, R-19: ოპერაციული რისკები

## მიმოხილვა

შენი პლატფორმა ძლიერ არის დამოკიდებული მესამე მხარის სერვისებზე. როცა რომელიმე მათგანი ჩაიშლება, ფასს შეიცვლის ან პოლიტიკას შეცვლის, მთელი პროდუქტი ზემოქმედების ქვეშ ექცევა. ეს ნორმალურია თანამედროვე SaaS-ისთვის, მაგრამ საჭიროა საგანგებო გეგმები.

## R-11: Anthropic API-ზე დამოკიდებულება

**ალბათობა:** Medium | **ზემოქმედება:** High | **პრიორიტეტი:** P2

### ერთი წერტილის ჩავარდნა

Claude API არის შენი თარგმანის pipeline-ის გული. თუ Anthropic-ის API მიუწვდომელია, შენი ძირითადი პროდუქტი ჩერდება. სარეზერვო თარგმანის პროვაიდერი არ არის იმპლემენტირებული.

### რისკის სცენარები

| სცენარი | ალბათობა | ზემოქმედება | აღდგენის დრო |
|---------|----------|------------|-------------|
| API-ის გათიშვა (საათები) | საშუალო | მაღალი — რიგში მყოფი job-ები ჩავარდება | საათები |
| API rate limit-ის მიღწევა | მასშტაბში მაღალი | საშუალო — ნელი დამუშავება | წუთები-საათები |
| ფასის ზრდა | საშუალო | საშუალო — მარჟის შეკუმშვა | კვირები ადაპტაციისთვის |
| პოლიტიკის ცვლილება (IP შეზღუდვები) | დაბალი-საშუალო | კრიტიკული — შეიძლება use case დაბლოკოს | კვირები-თვეები |
| მოდელის ქცევის ცვლილება (ხარისხის ცვლილება) | საშუალო | საშუალო — თარგმანის ხარისხი იცვლება | მიმდინარე |
| API key-ის გაუქმება (პოლიტიკის დარღვევა) | დაბალი | კრიტიკული — სრული გაჩერება | დღეები-კვირები |

### რა უკვე გაქვს

- BullMQ job queue retry ლოგიკით
- Chunked თარგმანი (წიგნი დაყოფილია სექციებად)
- Glossary/context management წიგნის მიხედვით

### რა აკლია

| ხარვეზი | მიტიგაცია |
|---------|----------|
| სარეზერვო თარგმანის პროვაიდერი არ არის | თარგმანის ინტერფეისის აბსტრაქცია, Google Translate-ის ან DeepL-ის დამატება fallback-ად |
| Circuit breaker არ არის | Circuit breaker pattern-ის იმპლემენტაცია API გამოძახებებისთვის |
| Per-job ხარჯის თვალყურის დევნება არ ხდება | Per-translation ხარჯის ლოგირების დამატება (გამოყენებული token-ები, API ხარჯი) |
| ხარჯის შეტყობინებები არ არის | შეტყობინებების დაყენება, როცა დღიური/თვიური API ხარჯი ზღვარს გადააჭარბებს |
| ხარისხის მონიტორინგი არ არის | დასრულებული თარგმანების პერიოდული sample-check |

### მიტიგაციის სტრატეგია

**მოკლევადიანი (P2):**
1. Circuit breaker pattern-ის დამატება: N თანმიმდევრული ჩავარდნის შემდეგ ახალი job-ების პაუზა და შეტყობინება
2. Per-job ხარჯის თვალყურის დევნის იმპლემენტაცია (input/output token რაოდენობის ლოგირება)
3. მკაცრი თვიური ხარჯის ლიმიტის დაყენება შეტყობინებებით 80% ზღვარზე
4. Exponential backoff-ით retry-ს დამატება (BullMQ კონფიგურაციის გადამოწმება)

**საშუალოვადიანი:**
1. თარგმანის აბსტრაქცია provider ინტერფეისის უკან
2. Google Translate-ის დამატება დაქვეითებული ხარისხის fallback-ად
3. დასრულებულ თარგმანებზე ხარისხის შეფასების იმპლემენტაცია
4. ხშირად გამოყენებული ფრაზების/გლოსარების cache API გამოძახებების შესამცირებლად

## R-13: TTS Storage ხარჯის ექსპლოზია

**ალბათობა:** Medium | **ზემოქმედება:** Medium | **პრიორიტეტი:** P2

### მათემატიკა

300-გვერდიანი წიგნი აუდიოდ გარდაქმნილი წარმოქმნის დაახლოებით 10-15 საათის აუდიოს. გონივრული ხარისხით:

| ფორმატი | ზომა საათზე | 300-გვერდიანი წიგნი | 1000 მომხმარებელი x 1 წიგნი |
|---------|-------------|---------------------|----------------------------|
| MP3 128kbps | ~56 MB | ~700 MB | ~700 GB |
| MP3 64kbps | ~28 MB | ~350 MB | ~350 GB |
| OGG Vorbis | ~40 MB | ~500 MB | ~500 GB |

S3 storage ღირს ~$0.023/GB/თვეში. Transfer ღირს ~$0.09/GB.

| მასშტაბი | თვიური storage | თვიური transfer (1 მოსმენა თითოეულზე) | ჯამი |
|----------|----------------|---------------------------------------|------|
| 100 მომხმარებელი, 1 წიგნი | ~70 GB = $1.61 | ~70 GB = $6.30 | ~$8 |
| 1,000 მომხმარებელი, 1 წიგნი | ~700 GB = $16.10 | ~700 GB = $63 | ~$79 |
| 10,000 მომხმარებელი, საშ. 3 წიგნი | ~21 TB = $483 | ~21 TB = $1,890 | ~$2,373 |

შემოსავალი 10,000 მომხმარებლით TTS addon-ით: დამოკიდებულია TTS ფასდადებაზე, მაგრამ ხარჯები შემოსავალს სწრაფად შეიძლება გაუსწროს.

### TTS-ის დამატებითი ხარჯის ფაქტორები

- **გენერაციის ხარჯი:** Google Cloud TTS-ს, ElevenLabs-ს, Azure-ს თითოეულს per-character ფასდადება აქვს
- **დუბლირებული გენერაცია:** იგივე წიგნის თარგმანი რამდენიმე მომხმარებლის მიერ ცალ-ცალკე აუდიოს ქმნის
- **Streaming vs download:** Streaming განმეორებით data transfer-ს მოითხოვს
- **წინასწარი გენერაციის ხარჯვა:** აუდიოს გენერაცია, რომელსაც მომხმარებლები არასოდეს მოუსმენენ

### მიტიგაცია

| სტრატეგია | ეფექტი | სირთულე |
|-----------|--------|---------|
| მოკლევადიანი presigned URLs (უკვე იმპლემენტირებული: 1სთ) | URL-ის გაზიარების პრევენცია | შესრულებული |
| დაბალი აუდიო bitrate (64kbps მეტყველებისთვის საკმარისია) | 50% storage-ის შემცირება | დაბალი |
| On-demand გენერაცია (არ გენერირდეს ყველა თავი წინასწარ) | ხარჯვის შემცირება | საშუალო |
| აუდიოს დედუპლიკაცია იგივე წყარო ტექსტისთვის | მნიშვნელოვანი დაზოგვა გაზიარებული კატალოგისთვის | საშუალო |
| CDN caching პოპულარული კონტენტისთვის | S3 transfer ხარჯების შემცირება | საშუალო |
| აუდიოს ავტო-წაშლა არააქტიურობის პერიოდის შემდეგ | Storage-ის შემცირება | დაბალი |
| Streaming proxy პირდაპირი S3-ის ნაცვლად | წვდომის კონტროლი, DRM-ის დამატება | მაღალი |

### რეკომენდებული მიდგომა

1. აუდიოს გენერაცია on-demand თავის მიხედვით, არა მთელი წიგნი ერთბაშად
2. აუდიოს retention-ის დაყენება: წაშლა 90 დღის არაწვდომის შემდეგ, მოთხოვნისას ხელახლა გენერაცია
3. 64kbps MP3-ის გამოყენება მეტყველებისთვის (სავსებით ადეკვატური ხარისხი)
4. კერძო თარგმანებისთვის: აუდიო მომხმარებლისთვის კერძოა, დედუპლიკაცია არ ხდება
5. ლიცენზირებული კატალოგისთვის (მომავალში): აუდიოს დედუპლიკაცია მომხმარებლებს შორის

## R-19: Vendor Lock-in

**ალბათობა:** Low | **ზემოქმედება:** Medium | **პრიორიტეტი:** P3

### ამჟამინდელი დამოკიდებულებები

| სერვისი | Vendor | Lock-in-ის დონე | ალტერნატივა |
|---------|--------|-----------------|-------------|
| AI თარგმანი | Anthropic Claude | **მაღალი** — prompt engineering სპეციფიკურია Claude-სთვის | Google Gemini, OpenAI GPT, DeepL |
| TTS (ძირითადი) | Google Cloud TTS | საშუალო | ElevenLabs, Azure (უკვე ინტეგრირებული) |
| TTS (პრემიუმ) | ElevenLabs | დაბალი | Google Cloud, Azure |
| Storage | AWS S3 | დაბალი | Google Cloud Storage, Azure Blob |
| Email | Resend | დაბალი | SendGrid, AWS SES, Mailgun |
| ბაზა | PostgreSQL | ძალიან დაბალი | სტანდარტული SQL, ნებისმიერი პროვაიდერი |
| რიგი | Redis + BullMQ | დაბალი | AWS SQS, RabbitMQ |
| გადახდები | BOG Pay + TBC Pay | **მაღალი** — ქართული ბაზრისთვის სპეციფიკური | საქართველოში შეზღუდული ალტერნატივები |
| მონიტორინგი | Sentry | დაბალი | Datadog, New Relic, self-hosted |

### ყველაზე მაღალი რისკის Vendor-ები

1. **Anthropic** — ძირითადი პროდუქტის დამოკიდებულება. პირდაპირი ალტერნატივა არ არსებობს, რომელიც იგივე ხარისხის ქართულ თარგმანს აწარმოებს. მიტიგაცია: provider abstraction layer.
2. **BOG/TBC** — ერთადერთი რეალური გადახდის ვარიანტები ქართულ ბაზარზე. მიტიგაცია: ორივეს მხარდაჭერა (უკვე შესრულებული).
3. **AWS S3** — დიდი მონაცემების მიგრაციის ხარჯი გადართვისას. მიტიგაცია: S3-თავსებადი API, რომელსაც ალტერნატივები იყენებენ (GCS, MinIO).

### მიტიგაცია (P3)

1. Provider-სპეციფიკური კოდის შენარჩუნება abstraction ინტერფეისების უკან (ნაწილობრივ შესრულებული TTS-ით)
2. თითოეული vendor-ის API ინტეგრაციის წერტილების დოკუმენტირება
3. vendor-სპეციფიკური ფუნქციების თავიდან აცილება, რომლებსაც ეკვივალენტები არ აქვთ სხვაგან
4. ტესტირება მინიმუმ 2 TTS პროვაიდერით (უკვე შესრულებული)

## ოპერაციული მონიტორინგის ხარვეზები

| სფერო | ამჟამინდელი მდგომარეობა | რეკომენდებული |
|-------|------------------------|-------------|
| API ხარჯის თვალყურის დევნება | არ არის იმპლემენტირებული | Per-job token/ხარჯის ლოგირება |
| თარგმანის რიგის ჯანმრთელობა | BullMQ dashboard შესაძლებელია | მონიტორინგის dashboard-ის დაყენება |
