# R-07, R-08, R-15, R-17, R-18: ტექნიკური უსაფრთხოების რისკები

## მიმოხილვა

შენი კოდბეისის უსაფრთხოების საფუძველი მყარია (7/10 სიმწიფე). Auth კარგად არის იმპლემენტირებული rate limiting-ით, timing-safe comparison-ებით და token versioning-ით. File upload-ს აქვს extension allowlist, magic bytes, MIME check-ები და filename sanitization. მაგრამ არის კონკრეტული ხარვეზები, რომლებსაც ყურადღება სჭირდება.

## R-07: Reader Service-ის Authorization ხარვეზი

**ალბათობა:** High | **ზემოქმედება:** High | **პრიორიტეტი:** P1

### პრობლემა

Reader სერვისი (bookmarks, highlights, notes, reading progress) **არ ამოწმებს წიგნის ownership-ს** ჩანაწერების შექმნისას. მომხმარებელს შეუძლია:

1. სანიშნეების/მონიშვნების დამატება წიგნებზე, რომლებიც არ ეკუთვნის
2. კითხვის პროგრესის შექმნა ნებისმიერი წიგნისთვის ID-ით
3. პოტენციურად წიგნის შინაარსის ენუმერაცია შეცდომის შეტყობინებებიდან

### კოდბეისის მტკიცებულება

სხვა სერვისები სწორად ამოწმებენ ownership-ს:
- Books: `verifyOwnership()` update/delete-ზე
- Translations: ამოწმებს `userBooks` ურთიერთობას
- TTS: ვალიდაცია book/translation ownership-ზე
- Payments: ამოწმებს წიგნის ownership-ს თარგმანის გადახდებისთვის

მაგრამ Reader სერვისი userId-ს გადასცემს წიგნზე წვდომის შემოწმების გარეშე.

### გამოსწორება

Ownership-ის ვერიფიკაციის დამატება ყველა Reader endpoint-ზე:

```typescript
// დაამატე BookmarkService-ში, HighlightService-ში, NoteService-ში, ReadingProgressService-ში
private async verifyBookAccess(userId: string, bookId: string) {
  const userBook = await this.prisma.userBook.findFirst({
    where: { userId, bookId },
  });
  if (!userBook) throw new ForbiddenException();
}
```

### Severity-ის დასაბუთება

ეს არის P1, არა P0, რადგან:
- პირდაპირ არ ააშკარავებს წიგნის შინაარსს (Reader ინახავს მომხმარებლის შექმნილ მეტამონაცემებს, არა წიგნის ტექსტს)
- ექსპლუატაციისთვის საჭიროა ვალიდური bookId მნიშვნელობების ცოდნა
- მაგრამ არღვევს OWASP-ის Broken Object Level Authorization-ს (API Security #1) და შეიძლება გამოიწვიოს მონაცემთა ინტეგრაციის პრობლემები

## R-08: ანტივირუსული სკანირება არ ხდება Upload-ზე

**ალბათობა:** Medium | **ზემოქმედება:** High | **პრიორიტეტი:** P1

### ამჟამინდელი მდგომარეობა

შენს upload pipeline-ს კარგი პირველი ხაზის დაცვა აქვს:
- Extension allowlist (.pdf, .epub, .txt, .docx, .zip)
- MIME type ვალიდაცია
- Magic byte ვერიფიკაცია (PDF, ZIP-ზე დაფუძნებული ფორმატები)
- 50MB ზომის ლიმიტი
- Filename sanitization (წაშლის HTML-ს, path traversal-ს, სპეციალურ სიმბოლოებს)
- Upload rate limiting (5 ატვირთვა 15 წუთში)

### რა აკლია

- ანტივირუსული/მავნე პროგრამების სკანირება
- DOCX-ში ჩაშენებული შესრულებადი ფაილების (მაკროების) სკანირება
- PDF-ში მავნე JavaScript-ის აღმოჩენა
- Content Disarm and Reconstruct (CDR)

### რეალური საფრთხეები

| საფრთხე | ვექტორი | ზემოქმედება |
|---------|---------|------------|
| მავნე PDF | JavaScript/exploit PDF-ის სტრუქტურაში | სერვერის კომპრომეტაცია parser-ის მეშვეობით |
| DOCX მაკრო | VBA მაკრო ატვირთულ Word ფაილში | კოდის შესრულება parsing worker-ში |
| Zip bomb | ჩადგმული ZIP EPUB/DOCX-ში | Worker-ის მეხსიერების ამოწურვა, რიგის ჩაჭედვა |
| Parser exploit | შემუშავებული ფაილი იწვევს ხარვეზს PDF/EPUB parser-ში | Crash ან RCE |

### მიტიგაციის ვარიანტები

| ვარიანტი | ხარჯი | ეფექტურობა | რეკომენდაცია |
|----------|-------|------------|-------------|
| ClamAV (ღია კოდი) | უფასო, self-hosted | კარგი საწყისი | **MVP არჩევანი** |
| AWS Lambda + ClamAV | ~$0.20/1000 სკანი | კარგი, serverless | კარგია production-ისთვის |
| VirusTotal API | უფასო tier ხელმისაწვდომი | შესანიშნავი აღმოჩენა | Privacy-ის პრობლემა — ფაილები იგზავნება მესამე მხარესთან |
| Sandbox parsing | საშუალო (იზოლირებული კონტეინერები) | შესანიშნავი parser exploit-ებისთვის | საუკეთესო მასშტაბისთვის |

**რეკომენდაცია:** დაიწყე ClamAV სკანირებით ფაილების parsing pipeline-ში გადაცემამდე. დაამატე parser-ის timeout ლიმიტები (ნაწილობრივ უკვე იმპლემენტირებულია BullMQ job timeout-ებით).

### დამატებითი გამაგრება

- უარყავი დაშიფრული/პაროლით დაცული PDF-ები (ვერ ასკანირებ შინაარსს, ვერ დაპარსავ სანდოდ)
- დააწესე მაქსიმალური გვერდების ლიმიტი upload-ზე (მაგ., 2000 გვერდი)
- დააწესე ამოღებული სიმბოლოების მაქსიმალური ლიმიტი (მეხსიერების ამოწურვის პრევენცია parsing-ისას)
- გამორთე მაკროების შესრულება DOCX parsing-ში (გადაამოწმე შენი parser ბიბლიოთეკის ქცევა)

## R-15: SMS OTP რეალურად არ არის იმპლემენტირებული

**ალბათობა:** High | **ზემოქმედება:** Low | **პრიორიტეტი:** P2

### პრობლემა

Auth სერვისს აქვს OTP ლოგიკა (გენერაცია, Redis-ში შენახვა, timing-safe comparison-ით ვერიფიკაცია, rate limit), მაგრამ ფაქტობრივი SMS-ის გაგზავნა **არ არის იმპლემენტირებული**. OTP ინახება Redis-ში, მაგრამ არასოდეს ეგზავნება მომხმარებლის ტელეფონს.

### რისკი

- ფუნქცია, როგორც ჩანს, მუშაობს, მაგრამ OTP-ს არ აწვდის
- მომხმარებლები, რომლებიც ტელეფონით ვერიფიკაციას აირჩევენ, ჩარჩებიან
- თუ ტელეფონით ვერიფიკაციას რეკლამირებ, ეს დაუსრულებელი ფუნქციაა

### მიტიგაცია

ერთ-ერთი:
1. **SMS-ის გაგზავნის იმპლემენტაცია** Twilio-ით ან ადგილობრივი ქართული SMS პროვაიდერით
2. **ტელეფონის OTP ფუნქციის წაშლა** UI-დან, სანამ მზად არ იქნება
3. **დოკუმენტირება როგორც „მალე"** და flow-ს გათიშვა

## R-17: Secret Rotation მექანიზმის არარსებობა

**ალბათობა:** Low | **ზემოქმედება:** High | **პრიორიტეტი:** P3

### ამჟამინდელი მდგომარეობა (კარგი)

- ყველა საიდუმლო იტვირთება environment variables-იდან
- კოდში hardcoded საიდუმლოები არ არის
- Startup ვალიდაცია ვარდება, თუ საჭირო საიდუმლოები აკლია production-ში
- `.env` არის `.gitignore`-ში

### რა აკლია

- საიდუმლოების პერიოდული როტაციის მექანიზმი
- ინტეგრაცია secrets manager-თან (AWS Secrets Manager, HashiCorp Vault)
- GitHub secret scanning ავტომატიზაცია
- გასაღებების როტაციის პროცესის დოკუმენტაცია

### რისკის ქვეშ მყოფი საიდუმლოები

| საიდუმლო | კომპრომეტაციის ზემოქმედება |
|----------|--------------------------|
| `ANTHROPIC_API_KEY` | არაავტორიზებული API-ს გამოყენება, დიდი ანგარიშები |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | მომხმარებლის სრული იმიტაცია |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | მონაცემთა გაჟონვა, ფაილებზე წვდომა/წაშლა |
| `BOG_CLIENT_SECRET` / `TBC_API_SECRET` | გადახდის თაღლითობა |
| `VAPID_PRIVATE_KEY` | Push notification-ის ბოროტად გამოყენება |

### მიტიგაცია (P3 — მასშტაბის ეტაპი)

1. თითოეული საიდუმლოსთვის როტაციის პროცედურის დოკუმენტირება
2. კალენდარში შეხსენებების დაყენება 90-დღიანი როტაციისთვის
3. ბიუჯეტის დაშვებისას მიგრაცია AWS Secrets Manager-ზე
4. GitHub secret scanning-ის ჩართვა რეპოზიტორიაზე

## R-18: Soft-Delete / Audit Trail არ არსებობს

**ალბათობა:** Low | **ზემოქმედება:** Medium | **პრიორიტეტი:** P3

### ამჟამინდელი მდგომარეობა

- ანგარიშის წაშლა cascade-ით hard-delete-ს აკეთებს ყველაფერზე
- აუდიტის ლოგი, თუ ვინ რა გააკეთა და როდის, არ არსებობს
- ფაქტის შემდეგ გამოძიების შესაძლებლობა არ არის

### რატომ აქვს მნიშვნელობა

- თუ უფლებების მფლობელი იკითხავს „როდის იყო ეს კონტენტი შენს პლატფორმაზე?" პასუხის გაცემა ვერ შეძლებ
- თუ მომხმარებელი გადახდას გაასაჩივრებს, აუდიტის კვალი გადახდის ჩანაწერის მიღმა არ გაქვს
- Production-ის პრობლემების debugging უფრო რთულია აუდიტის ლოგების გარეშე
- Compliance-ის გამოძიებები ისტორიულ ჩანაწერებს მოითხოვს

### მიტიგაცია

1. მარტივი `AuditLog` ცხრილის დამატება: `userId, action, resourceType, resourceId, metadata, createdAt`
2. ძირითადი მოქმედებების ლოგირება: upload, თარგმანის დაწყება/დასრულება, გადახდა, წაშლა, ანგარიშის ცვლილებები
3. კონტენტის soft-delete-ის განხილვა (`deletedAt` სვეტის დამატება) retention პერიოდის შემდეგ პერიოდული hard-delete-ით

## რა არის უკვე კარგად იმპლემენტირებული (დამსახურება სადაც ეკუთვნის)

ეს სფეროები ChatGPT-ის ანალიზში პრობლემატურად იყო მითითებული, მაგრამ რეალურად **სწორად არის დამუშავებული** შენს კოდბეისში:

| სფერო | იმპლემენტაცია |
|-------|--------------|
| Login rate limiting | 10 მცდელობა 15 წუთში, fail-closed |
| OTP უსაფრთხოება | 1/წთ გაგზავნის cooldown, 5 მაქს. მცდელობა, timing-safe comparison |
| პაროლის უსაფრთხოება | bcrypt hashing, constant-time comparison |
| Token versioning | ინვალიდაცია password change / logout-all-ზე |
| ანგარიშის ენუმერაცია | Dummy bcrypt გამოძახება არარსებული მომხმარებლებისთვის |
| File upload ვალიდაცია | Extension allowlist + MIME + magic bytes + size limit |
| Filename sanitization | Path traversal-ის, HTML-ის, სპეციალური სიმბოლოების წაშლა |
| S3 უსაფრთხოება | Presigned URLs (1სთ TTL), AES256 encryption, attachment disposition |
| Payment webhooks | HMAC-SHA256 signature ვერიფიკაცია, timing-safe, idempotency guard |
| გლობალური rate limiting | 100 req/min production-ში, endpoint-სპეციფიკური ლიმიტები |
| Input ვალიდაცია | გლობალური validation pipe whitelist-ით, Prisma parameterized queries |
| უსაფრთხოების headers | Helmet.js ჩართული, CORS შეზღუდული |
